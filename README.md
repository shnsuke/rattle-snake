# Rattlesnake VO2max Trainer

サイクリングのVO2max向上インターバル「Rattlesnake」ワークアウトを解析し、同じ構造のまま強度を段階的に変化させて漸進的オーバーロードを行うための、オフライン動作するトレーニングアプリ。

## 1. 元ワークアウトの評価

`data/rattlesnake_original_ride.csv`（実走データ）を解析した結果:

| 項目 | 値 |
|---|---|
| 総時間 | 約66分 |
| 推定FTP | 約312W（区間ごとの平均パワー ÷ 強度%から逆算） |
| 平均パワー | 約223W |
| 推定NP | 約269W |
| 推定IF | 約0.86 |
| 推定TSS | 約80 |
| VO2max帯(≥105%FTP)滞在時間 | 約21分 |

### 構造

```
ウォームアップ 15:00 @ 55%FTP
├─ セット1: キック 57s@128% → [30s@105-110% / 15s@50-52%] × 11-12本
├─ 回復 5:16 @ 62%FTP
├─ セット2: キック 58s@128% → [29-30s@105-110% / 15-17s@50-55%] × 12本
├─ 回復 5:16 @ 62%FTP
├─ セット3: キック 58s@128% → [29-30s@105-110% / 15-17s@50-54%] × 12本
クールダウン 10:31 @ 43%FTP
```

各セット冒頭の約60秒・128%FTPの「キック」は、酸素摂取のキネティクスを前倒しして素早くVO2maxに到達させるための定番テクニックで、その後に続く 30秒オン/15秒オフ（いわゆる**30/15プロトコル**、Billatらの研究に基づく高頻度インターバル）で、1本あたりの平均強度を上げずにVO2max帯の総滞在時間を稼ぐ設計になっている。

### 評価コメント

- **良い点**: 30/15sの短いオン/オフは乳酸を溜めすぎずにVO2max刺激を最大化できる、効率の良い設計。キックによる立ち上がりの工夫も理にかなっている。セット間5分強度62%の回復は、次セットのキックに耐えられる程度に呼吸循環系をクールダウンしつつ完全休息はさせない、ちょうど良い設定。
- **気になる点**: 実走データではセット1の終盤で1本だけ61秒・77%という長めの緩い区間が入っている（本来16秒/50%であるべき箇所）。疲労やペーシングミスの可能性があり、セット1後半のペース管理に注意すると良い。
- **負荷**: TSS約80・IF約0.86は「高強度インターバル日」として妥当。前後に軽い日を置くことを推奨。

## 2. 強度バリエーション（漸進的オーバーロード）設計

レベル3「Original Rattlesnake」は、Bent Rønnestadの30:15プロトコル（30秒オン・15秒レストを13本×3セット＝計39本）を再現した公開Zwiftワークアウトの構成に合わせて校正してある: 各セット冒頭に**60秒・140%FTPのキック**を入れて素早くVO2maxへ到達させ、続く13本は**120%FTPから110%FTPへ徐々に強度を落とす「ラダー」構成**（1本ごとに強度が一定ではない）。ウォームアップは45%→65%→80%の3段階ランプ(3分ずつ)、セット間回復とクールダウンはそれぞれ3分。

同じ「キック＋ラダー式30/15秒インターバル×3セット」という**ワークアウトの骨格は変えず**、以下の独立した軸を段階的に動かすことでレベル分けした（`js/progression.js`）。

- **ラダーの上限・下限** (`ladderStart`/`ladderEnd`): 110→102%FTP 〜 126→116%FTP
- **オフ強度 / 深さ** (`offPower`): 55% → 46%FTP（下げるほど回復が浅くなり負荷UP）
- **本数・セット数** (`reps`, `sets`): 9本×2セット → 15本×3セット
- **セット間回復時間** (`interSetRecovery`): 210秒 → 150秒（短縮するほど密度UP）
- 上級レベルではオン/オフ秒数自体を30/15秒→40/20秒に伸長し、1本あたりのVO2max滞在時間を延長

| Lv | 名称 | 週 | 構成 | 時間 | TSS | IF | VO2max滞在 |
|---|---|---|---|---|---|---|---|
| 0 | Deload / Easy | 回復週 | 2set×9本 25/15s 110→102% | 29分 | 35 | 0.86 | 7分 |
| 1 | Base 1 | 第1週 | 3set×11本 30/15s 115→106% | 45分 | 66 | 0.94 | 19分 |
| 2 | Base 2 | 第2週 | 3set×12本 30/15s 118→108% | 47分 | 74 | 0.97 | 21分 |
| 3 | **Original** | 第3週(基準) | 3set×13本 30/15s 120→110% | 50分 | 82 | 1.00 | 23分 |
| 4 | Build 1 | 第4週 | 3set×14本 30/15s 122→112% | 52分 | 88 | 1.02 | 24分 |
| 5 | Build 2 | 第5週 | 3set×15本 30/15s 124→114% | 54分 | 95 | 1.03 | 26分 |
| 6 | Peak 1 | 第6週 | 3set×13本 40/20s 124→114% | 58分 | 106 | 1.04 | 29分 |
| 7 | Peak 2/Test | 第7週 | 3set×14本 40/20s 126→116% | 61分 | 115 | 1.06 | 31分 |

数値はアプリ内 `RSWorkout.analyze()` による推定値（FTP=312W時）。TSSは区間平均パワーからの簡易NP推定に基づく近似値。「構成」の強度2値はラダーの開始%→終了%（キック強度は別途140%前後）。

レベル3が参照元のZwiftワークアウトにほぼ一致するよう調整してあり、そこを起点に前後へ無理なく漸進できるようにしてある。各レベルはアプリの「③提案」タブでカスタム入力（ラダー開始/終了・本数・セット数など）からさらに微調整でき、`.zwo`（Zwiftワークアウト）としてエクスポートしてERGモードで実走することもできる。ZWOのIntervalsT要素は本ごとに強度を変えられないため、ラダーは参照元のZwiftワークアウト自体と同じく、本ごとの個別SteadyStateブロックの並びとして書き出している。

## 3. アプリ設計（オフライン動作）

### 方針

- **フレームワーク・ビルド不要の静的Webアプリ (PWA)**。ネイティブアプリ化やサーバーを使わず、`index.html` をブラウザで開くだけで動く。GitHub Pages 等の静的ホスティングにそのまま置ける。
- **完全ローカル完結**: FTP設定・トレーニング履歴は `localStorage` にのみ保存。外部への送信は一切なし。
- **Service Worker によるオフラインキャッシュ**: 初回読み込み後はネットワークが無くても起動・実行可能（キャッシュ優先＋バックグラウンド更新戦略）。ホーム画面に追加すればアプリのように使える。
- **サウンド生成はWeb Audio APIでその場生成**: 音源ファイルを持たないため追加のネットワーク取得が不要で、オフラインインストールが軽量。

### モジュール構成

```
index.html            アプリシェル（タブ切り替えUI）
css/style.css         レスポンシブ・ダーク/ライト対応スタイル
js/workout.js         ワークアウトのブロック定義(steady/intervals/ladder)→区間展開、TSS/NP/IF/ゾーン解析
js/progression.js     8段階の強度レベル定義(ラダー式)とテンプレート生成
js/chart.js           Canvasでのパワープロファイル描画（外部chartライブラリ不使用）
js/player.js          ドリフト補正付きタイマー、音声キュー、Wake Lock
js/storage.js         FTP・アップロード済みライドのlocalStorage永続化
js/csvimport.js       実走CSV（同フォーマット）の読み込み・解析
js/suggest.js         アップロードされたライドからレベル判定・後半失速の評価・次回レベル提案を行うルールベースエンジン
js/export.js          Zwift .zwo エクスポート
js/app.js             上記モジュールを結線するUIコントローラ
manifest.webmanifest  PWAマニフェスト
service-worker.js     オフラインキャッシュ
data/                 元の実走CSV（比較・デモ用）
```

依存ライブラリはゼロ（CDNフェッチも無し）。これにより、ネットワークが不安定なジムや屋外でも常に同じ挙動で動作する。

### 画面（タブ）

1. **①ホーム** — 直近にアップロードしたワークアウトの評価（統計・パワーグラフ・ゾーン分布）と、それに基づく次回ワークアウトの提案サマリー
2. **②アップロード** — 実走CSVをアップロードすると自動で解析され、この端末に記録される
3. **③提案** — 直近ライドの判定根拠（レベル判定・後半失速の評価）と、それに基づき自動選択された推奨レベルの詳細。0〜7の強度レベルを手動で選び直したり、カスタム微調整、`.zwo`エクスポート、実行タブへの送信もここで行う
4. **④総合評価** — これまでアップロードした全ワークアウトを通した傾向（レベル・TSSの推移、傾向コメント、個別履歴一覧）
5. **実行** — フォローアロー式タイマー。現在区間・目標W・残り時間をHUD表示、音声キュー（区間切替音＋残り3-2-1カウント）、進捗バー付きパワーグラフ、画面スリープ抑制(Wake Lock API対応端末)
6. **設定** — FTP設定（%FTP基準の全計算はここから再計算される）

初回起動時は、①〜④が空にならないよう `data/rattlesnake_original_ride.csv`（元の実走データ）が自動的に最初の1件としてアップロード履歴に取り込まれる。

### 次回ワークアウトの提案ロジック（`js/suggest.js`）

1. アップロードされた区間データを、秒数とパワーの形状から「キック」「オン」「オフ」に自動分類する（レベルごとに数値は違っても、同じ構造なので分類ロジックは共通）。
2. オン区間の平均パワー・本数・秒数を8段階のレベル定義と比較し、最も近いレベルを「今回の判定レベル」とする。
3. 判定レベルのラダー（本ごとの目標%FTP）を実際の本数に合わせて再構成し、各本の実測値をその目標値と比較した「計画比」を算出。ラダー自体が本ごとに強度を下げていく設計なので、単純な前半後半の実測パワー比較では常に「後半失速」と誤判定してしまう——それを避けるため、常に計画値との比を見て前半・後半で比較する（7%超の低下で顕著な失速、3〜7%で軽度、3%未満なら安定と判定）。
4. 顕著な失速なら1段階易しいレベルへ、軽度の失速なら同じレベルをもう一度、安定していれば1段階上のレベルを次回提案する。

### なぜこの設計か

- ワークアウトを「固定の区間データ」ではなく「パラメータ化されたテンプレート」として持つことで、Rattlesnakeという“型”を保ったまま無限にバリエーション（週ごとの漸進、個人のFTPへの自動スケーリング）を生成できる。
- 解析ロジック(`analyze()`)をCSVインポートと共有しているため、①〜④のどの画面でも同じ指標（TSS, NP, IF, ゾーン滞在時間）で評価できる。
- 提案ロジックはブラックボックスにせず、判定根拠（後半失速率など）を③タブに必ず表示することで、なぜそのレベルが提案されたか利用者が確認・上書きできるようにしている。
- PWA + localStorage + Service Worker という枯れた技術の組み合わせにより、追加のバックエンドやアカウント登録なしで「オフラインで完結するトレーニングアプリ」という要件を満たしている。

## 使い方

静的ファイルなので、任意のHTTPサーバーで配信するだけで動く（Service Worker登録のため `file://` ではなく `http(s)://` 経由を推奨）。

```bash
npx serve .
# もしくは
python3 -m http.server 8080
```

ブラウザで開いてホーム画面に追加すれば、以後オフラインでも起動できる。
